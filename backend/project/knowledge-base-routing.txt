Knowledge-base chat and summary routing

/ask -> query/analyzer.py -> documents/resolver.py -> orchestration/routing.py

- Structured QueryAnalysis separates summary, summary-all, document QA, cross-document QA and study-material requests. Study-material creation remains a distinct unsupported task until its agent is implemented; it is never silently converted into a summary.
- General QA searches all currently registered PDFs in the requested knowledge base. The frontend does not send the latest upload as document_id. An explicit document_id or outline scope restricts QA to that document; filenames in the question are resolved normally. document_order controls display order, not membership.
- Generic summaries with multiple available PDFs return JSON with real document IDs and a clarification message. document_id is an explicit QA target, not an implicit summary choice. With one available ready PDF, no clarification is needed.
- Exact filenames, normalized partial titles, list ordinals, and valid explicit conversation references are resolved against the server registry. Similar filenames and unknown names produce choices. Collections, all PDFs and the entire knowledge base are explicit multi-document scopes.
- Documents have processing, ready or failed status. An all-document request waits when any requested PDF is not ready. It never silently drops a processing/failed document.
- SQLite stores documents and expiring conversation state at backend/data/knowledge_base.sqlite3. Pending choices last 15 minutes and retain the original ordered candidate IDs, question, intent and format. New questions can replace a pending request. Ordinals never move to another file when an old choice is deleted.
- /documents/sync migrates historical local upload IDs by verifying stored Pinecone metadata; browser filenames are not trusted. Only the existing local knowledge base can adopt untagged historical uploads. Older documents without a stored outline need re-uploading for chapter summaries; full summaries still use all stored text.
- Uploads are registered as processing before indexing and become ready only after extraction, chunk ingestion and outline extraction succeed. The pipeline runs off the event loop so other requests can see processing state. Failed uploads remain visible. PDF storage uses generated document IDs, so duplicate filenames cannot overwrite each other's files.
- Chapter/selected-section summaries use stored outline boundaries and physical PDF pages. Unreliable, missing or ambiguous boundaries ask for clarification; there is no fallback to summarizing the whole PDF.
- The existing sequential summary agent loads all stored chunks, optionally filtered by the resolved chapter pages. Brief and key-points formats change final instructions. Each PDF gets its own labeled summary. Consolidation runs only when explicitly requested.
- Source coverage lists the PDF page ranges of the intermediate summaries. This is processing provenance, not independent verification of every generated claim. Existing grounding prompts still apply; no untested factual-verification guarantee is made.
- Normal QA continues through RetrievalAgent. Multi-PDF QA retrieves and reranks evidence per document, gives each nonempty group a place before supplementary passages, and enforces a shared context budget with document identity preserved. General QA can answer when some PDFs have no evidence; if none have evidence it returns the standard refusal. Explicit comparisons report missing evidence rather than implying full coverage. Insufficient budget is reported rather than silently dropping a represented document. Citations use the canonical PDF filename and page for each passage.
- The frontend handles clarification JSON and answer text at the same endpoint. DocumentChoices renders real ID-based options, supports typed replies, disables stale choices, and keeps readiness visible. Knowledge-base sync restores server state after reloads; conversation IDs separate pending choices and bounded completed-turn history. Follow-up retrieval and generation use scoped conversation context; see chat-continuity.md.

Scope: this is the existing local application, without user login. Registry queries and pending state are scoped by knowledge_base_id and conversation_id. These client-supplied IDs are not authentication. A hosted multi-user deployment must bind knowledge-base access and conversation ownership to an authenticated server principal; namespace filtering alone must not be presented as authorization.

Validation covers intent false positives, one/many/all PDFs, similar/unknown names, processing states, saved-order choices, expiration, deleted candidates, cross-knowledge-base membership, chapter boundaries, upload lifecycle, typed/clicked choices, consolidation, and normal QA. Provider calls are mocked in tests.
